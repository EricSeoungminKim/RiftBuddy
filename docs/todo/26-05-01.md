## Idea: Personalized Wake Word Calibration

Goal: improve wake word reliability by collecting the user's own pronunciation samples, similar to Siri setup.

### Proposed User Flow

1. First-run setup screen opens.
2. User repeats the wake phrase 5 times:
   - "Hey Buddy"
   - optionally "Hey Rift"
3. App records each sample.
4. App runs STT on each sample and stores:
   - raw transcript
   - confidence-like metadata if available
   - audio RMS profile
   - duration
   - detected variants
5. App suggests the best wake phrase variants based on what Whisper actually hears.

### Example

If user says "Hey Buddy" five times and Whisper hears:

- "hey buddy"
- "hey body"
- "hey buddy"
- "hey birdie"
- "hi buddy"

Then generate:

```env
RIFTBUDDY_WAKE_WORD_PHRASES="hey buddy,hey body,hey birdie,hi buddy"
```

### Technical Direction

- Add a calibration CLI first:
  - `python3 -m backend.voice.calibrate_wake_word`
- Later add frontend calibration UI.
- Store result in a local JSON file:
  - `backend/user_settings/wake_word_profile.json`
- Do not store raw voice clips by default unless user opts in.
- Keep only derived transcripts and phrase variants for privacy.

### Potential Accuracy Improvements

- Use `base.en` or `small.en` for wake detection.
- Use a rolling 4-second audio buffer instead of fixed 3-second chunks.
- Detect multiple possible mishearings.
- Add cooldown after detection to prevent duplicate triggers.
- Pause wake listening while Buddy TTS audio is playing.
- Add microphone input device selector.

## Idea: Wake Word Recognition Beyond STT

Current approach uses Whisper/faster-whisper STT:

```text
Audio -> speech-to-text -> check transcript for phrase
```

This is flexible, but not ideal for wake words because short phrases like "Hey Buddy" are easy for STT to miss.

The desired approach is closer to:

```text
Audio waveform/features -> wake-word classifier or calibrated signature -> trigger
```

This would allow the app to learn the user's voice pattern, pronunciation, amplitude profile, and timing from repeated samples.

### Can We Train It Like Siri?

Partially, yes. We probably should not train a full neural wake-word model immediately, but we can build a practical calibration layer first:

1. User records 5-10 samples of the wake phrase.
2. Extract audio features from each sample:
   - MFCC features
   - mel spectrogram
   - RMS/amplitude envelope
   - duration
   - pitch/energy pattern
3. During gameplay, compare rolling audio windows against those saved features.
4. Trigger wake word if similarity is above a threshold.

This is more robust than only saving possible transcript variants in `.env`.

Important note: raw amplitude/waveform matching alone is not enough. The same phrase can look different depending on mic gain, room noise, speaking speed, League audio, headset position, and whether the user is speaking quietly. Use amplitude as one feature, not the whole detector.

Better features:

- log-mel spectrogram
- MFCC
- speaker/wake embedding
- VAD-confirmed speech window
- duration and energy envelope
- optional STT confirmation

### Feature Matching Options

#### Option A: MFCC + Dynamic Time Warping

- Extract MFCC vectors from calibration samples.
- Extract MFCC vectors from live rolling audio.
- Compare using Dynamic Time Warping.
- Trigger if distance is below threshold.

Pros:

- No heavy ML training required.
- Personalized to the user's voice.
- Works offline.

Cons:

- Needs tuning to avoid false positives.
- Can be sensitive to microphone/background changes.

Libraries to evaluate:

- `librosa`
- `python_speech_features`
- `scipy`

#### Option B: OpenWakeWord

Use a dedicated wake word engine instead of Whisper.

Pros:

- Designed for always-on wake word detection.
- More efficient than repeated Whisper transcription.
- Supports custom model training paths.

Cons:

- Need to check macOS compatibility and packaging.
- Custom wake word training can be more involved.

Candidate:

- `openwakeword`

#### Option C: Porcupine / Picovoice

Commercial-grade wake word engine.

Pros:

- Very good wake word accuracy.
- Low CPU usage.
- Purpose-built for this exact problem.

Cons:

- API key/license constraints.
- Custom wake words may require account/tooling.
- Less open than local-only approach.

Candidate:

- Picovoice Porcupine

#### Option D: LiveKit Wake Word

Open-source wake word training/runtime built around custom wake words and modern wake-word model training.

Pros:

- Designed specifically for wake-word workflows.
- Supports custom models.
- Better long-term direction than STT-only phrase matching.

Cons:

- Need to verify macOS packaging, model size, CPU usage, and local development friction.
- More moving pieces than the current Whisper-only setup.

Candidate:

- `livekit-wakeword`

#### Option E: WebRTC VAD + Whisper Confirmation + Audio Similarity Hybrid

Hybrid approach:

1. Rolling audio checks similarity to user wake samples.
2. If similarity is close enough, run Whisper on that window.
3. Trigger only if either:
   - Whisper hears a known phrase, or
   - audio similarity is very high.

Pros:

- Better than either method alone.
- Reduces false positives.
- Can be built incrementally from current system.

Cons:

- More moving parts.

### Recommended Path

For production-grade wake detection, yes, we should eventually change the wake-word package. Keep Whisper/faster-whisper for Korean question transcription, but move the always-on wake listener to a purpose-built keyword spotting engine.

Recommended order:

1. Short-term: build **Option E** hybrid calibration on top of the current system.
2. Medium-term: evaluate **Porcupine** and **openWakeWord** side by side.
3. Long-term: choose one dedicated wake engine and remove repeated Whisper wake polling.

Why:

- Whisper is good for understanding questions.
- Wake-word detection is a different problem: always-on, short phrase, low latency, low false positives, low CPU.
- Dedicated wake engines are built around audio features/classifiers instead of transcript matching.

Initial implementation path:

1. Keep current Whisper wake detection.
2. Add wake calibration recording.
3. Extract and save MFCC/amplitude signatures.
4. Add a parallel similarity score on rolling audio.
5. Trigger when STT or similarity passes threshold.

This avoids replacing the whole wake system immediately while giving us a path toward Siri-like personalization.

## Idea: Context-Based Hotkey Questions

Current hotkey sends:

```text
What should I do right now?
```

Better approach: generate a deterministic, situation-aware question without using an LLM.

### Proposed Rule-Based Question Generator

Inputs from `GameState`:

- health percent
- current gold
- level
- CS
- KDA
- items
- game time
- recent events
- champion
- summoner spells
- estimated team gold
- estimated enemy team gold
- global gold difference
- objective timers
- death timers
- player lane matchup
- lane opponent item spike

### Example Rules

- If health < 30:
  - "내 체력이 낮은데 지금 귀환해야 해, 아니면 버텨도 돼?"
- If gold >= 2500:
  - "골드가 많이 쌓였는데 지금 귀환 타이밍을 잡아야 해?"
- If early game and CS is low:
  - "초반 CS가 부족한데 지금 라인 관리를 어떻게 해야 해?"
- If deaths > kills:
  - "지금 뒤처진 상황인데 안전하게 복구하려면 뭐 해야 해?"
- If recent event includes Dragon/Baron:
  - "다음 오브젝트 전에 뭘 준비해야 해?"
- If team/global gold is behind:
  - "우리 팀이 글로벌 골드에서 지고 있는데 이 게임을 어떻게 뒤집어야 해?"
- If global gold deficit is large:
  - "우리 팀이 전체 골드에서 크게 밀리고 있어. 무리하지 않고 역전하려면 지금 어떤 운영을 해야 해?"
- If team/global gold is ahead:
  - "우리 팀이 골드에서 앞서고 있는데 어떻게 굳혀야 해?"
- If player is behind but team is ahead:
  - "나는 라인에서 밀리고 있지만 팀은 앞서고 있어. 지금 어떻게 버스를 잘 타야 해?"
- If player is ahead but team is behind:
  - "나는 성장했지만 팀 전체는 밀리고 있어. 내 리드를 어디에 써야 역전각이 나와?"
- If objective spawns soon and team is behind:
  - "곧 오브젝트가 나오는데 우리 팀이 골드에서 밀려. 싸움을 피하고 교환할지, 준비해서 싸울지 판단해줘."
- If objective spawns soon and team is ahead:
  - "곧 오브젝트가 나오고 우리 팀이 앞서 있어. 안전하게 굳히려면 어떤 준비를 해야 해?"
- If enemy has objective momentum:
  - "상대가 오브젝트 흐름을 잡았는데 다음 싸움 전에 뭘 준비해야 해?"
- If player has shutdown risk:
  - "내가 현상금이 있을 때 어떻게 안전하게 리드를 굴려야 해?"
- If player is support with low vision:
  - "시야 점수가 낮은데 지금 어디를 먼저 밝혀야 해?"
- If top lane is isolated and teleport is available:
  - "텔레포트가 있을 때 사이드 운영을 계속해도 돼, 아니면 합류해야 해?"
- Default:
  - "현재 상황에서 가장 중요한 다음 행동은 뭐야?"

### Pre-Prompt Tag Examples

The planner should attach one or more deterministic context tags before calling the LLM.

Examples:

```text
[losing_global_gold]
우리 팀이 전체 골드에서 밀리고 있어. 지금부터 이길 수 있는 운영을 알려줘.
```

```text
[high_gold_reset]
내가 골드를 많이 들고 있어. 지금 귀환 타이밍을 잡아야 하는지 판단해줘.
```

```text
[objective_soon_behind]
곧 오브젝트가 나오는데 우리 팀이 불리해. 싸움, 교환, 시야 중 무엇을 우선해야 해?
```

```text
[ahead_protect_shutdown]
내가 앞서 있고 죽으면 현상금을 줄 위험이 있어. 어떻게 안전하게 리드를 굴려야 해?
```

This should be rule-based, not LLM-generated, so the hotkey stays fast and token usage stays low.
